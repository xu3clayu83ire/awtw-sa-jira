## 架構決策

### [2026-07-15] 網頁前端與核心自動化流程分階段開發，不一次做完
- **問題**：需求釐清時發現除了「文件產出 + Jira 自動建票」核心流程，還要有獨立網頁（輸入需求、瀏覽文件、進度儀表板），範圍比原先預期大，牽涉前端 + 後端 API 層
- **選項**：A. 網頁前端與核心自動化流程一起做，一次交付 / B. 分開：先做文件產出 + Jira 建票（核心），驗證跑通後再做網頁前端
- **決定**：選項 B
- **理由**：吸取 `awtw-short-url-service` 專案的教訓——一次疊加太多層（n8n + AWS 部署 + Notion 開票同時展開），中途卡在單一手動步驟就拖垮整條隊列，且事後很難分辨是規劃錯誤還是單一環節沒做完。核心自動化邏輯（文件產出、Jira 建票）先驗證可行，網頁只是這個核心能力的 UI 包裝，不影響核心功能驗收
- **取捨**：網頁前端會晚於核心功能完成，中間會有一段時間只能用 Claude Code 對話 + 手動看 tasks 文件確認進度，不能用網頁儀表板

### [2026-07-15] 不引入 Notion，文件事後編輯機制延後規劃
- **問題**：設計流程中拿掉了 Notion 中介（見「Webhook 觸發，不經 Notion 中介」技術決策），但使用者事後提出：文件產出後，非技術人員（需求提出單位、主管）要去哪裡改文件？目前沒有答案
- **選項**：A. 引入 Notion 當文件編輯/審閱介面（與短網址專案不同，那次是當開票觸發中介） / B. 本版不處理，先靠重跑 `/addyosmani-saspec` 對話或直接編輯 `.md` 檔案 / C. 併入 Frontend Phase 2 的獨立網頁做編輯功能
- **決定**：選項 B，先完成這一版，Notion（或其他編輯介面）留到下一版再加
- **理由**：核心目標是先驗證「文件產出 + Jira 自動建票」跑得通，编辑介面是次要需求，且還沒有明確答案要用 Notion 還是併入 Frontend 網頁，倉促決定容易又走回「一次設計太多」的老路
- **取捨**：本版文件如果要修改，只能技術人員自己編輯 `.md` 檔案或重跑對話，非技術人員暫時無法自行修改；已在 `requirement.md` 的「已知缺口」段落記錄，避免下次回來忘記為什麼沒做

### [2026-07-15] Frontend Phase 2 新增輕量 Node.js proxy 後端，避免 Jira 憑證曝露在前端
- **問題**：進度儀表板需要讀取 Jira 票狀態，若前端直接呼叫 Jira REST API，Jira API Token 就必須放在前端程式碼或瀏覽器可存取的地方，等於憑證公開曝露
- **選項**：A. 前端直接呼叫 n8n Webhook／Jira API，不另建後端 / B. 新建一層輕量 Node.js proxy，只服務「讀取 Jira 票狀態」這個需求，憑證存在 proxy 端
- **決定**：選項 B
- **理由**：文件產出觸發、n8n 建票 Webhook 呼叫不需要憑證（憑證在 n8n 端），可以前端直接呼叫；但讀 Jira 狀態這件事如果讓前端直接打 Jira API，就一定要曝露憑證，屬於不可接受的安全風險。只為了這一個需求新增最小範圍的 proxy，不做其他業務邏輯，避免過度設計
- **取捨**：多了一個要部署/維護的後端服務，比純前端方案複雜一點，但這是安全性換複雜度的必要取捨

### [2026-07-15] 「送出需求」不做完整自動化，只存成 _idea 檔案
- **問題**：Frontend T01 的需求輸入表單，原始描述是「送出後觸發文件產出流程」，但 `design.md` 定義的文件產出模組是 `/addyosmani-saspec`（Claude Code 互動對話），網頁後端沒辦法同步呼叫它拿到結果
- **選項**：A. 後端只把需求存成 `_idea/<日期時間>.md`，實際產文件仍由使用者回來跟 Claude Code 對話執行 / B. 後端直接接 Claude API，自己完成整個 saspec 流程，不需要人回來對話
- **決定**：選項 A
- **理由**：選項 B 是完全不同量級的工程（等於把 saspec 這個 skill 的邏輯用程式碼重新實作一次：多階段確認、決策管控、文件產出規則），今天已經因為範圍估算不準改過好幾次方向，不應該在這個時間點又滾雪球式擴大範圍
- **取捨**：「送出需求」目前不是真正的一鍵全自動，使用者送出後還是要回來跟 Claude Code 互動才能拿到產出的文件，只是省了手動建立 `_idea/` 檔案這個步驟

### [2026-07-15] 移除網頁需求輸入功能，前端只做純查詢
- **問題**：上一筆決策把「送出需求」縮小成「存成 `_idea/<日期時間>.md`」，實作完成並實測後，使用者指出：反正還是要回來跟 Claude Code 對話才能真正產出文件，網頁存檔這一步沒有實質省事，多繞一圈沒有意義
- **選項**：A. 保留（只是存檔，功能雖小但至少省了手動建 `_idea/` 檔案這個步驟）/ B. 移除，前端只保留查詢功能（文件檢視器、進度儀表板）
- **決定**：選項 B
- **理由**：Frontend Phase 2 的真正價值在「查詢」（看文件、看進度），不在「輸入」——輸入需求這件事本來就得跟 Claude Code 對話才能真正推進，網頁只是加一層儀式感，沒有解決任何實際痛點
- **異動範圍**：刪除 `RequirementForm.jsx`／`.test.jsx`、後端 `/api/requirements` 端點與測試；`App.jsx` 移除表單；`requirement.md`／`design.md`／`tasks-frontend.md`／`tasks-backend.md` 同步更新
- **取捨**：如果之後真的想要「網頁直接輸入需求就自動產文件」的體驗，必須後端接 Claude API 自己完成整個 saspec 流程（見上一筆決策的選項 B），屬於下一版才考慮的大工程，不是現在這種輕量調整能達成
