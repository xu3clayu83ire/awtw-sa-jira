# 需求文件 — SA 文件產出與 Jira 自動開票工具

> 本文件模擬需求提出單位的視角撰寫，描述「要什麼」，不描述「怎麼做」。

## 需求背景與痛點

團隊在啟動新功能開發前，SA 需要手動撰寫需求文件、系統設計文件，再手動把開發任務拆解、逐筆貼到 Jira 建票。這個過程重複性高、容易漏掉任務或角色標籤，而且一旦中途有人工設定卡住（例如環境憑證），SA 常常搞不清楚進度卡在哪，也難以回溯當初的決策脈絡。

## 期望達成的目標

有一套工具，能在收到一份需求描述後，自動產出三份文件（需求文件、系統設計文件、開發任務清單），並把開發任務直接建立到 Jira，讓 SA 不用手動搬運內容、團隊成員可以直接在 Jira 上看到自己負責的任務。

## 功能期望（業務角度）

1. 有一個獨立網頁，可以在上面瀏覽產出的三份文件、查看開發進度（不含需求輸入，見下方「已知缺口」）。
2. 提供需求描述後（透過與 Claude Code 對話），自動產出一份「需求文件」，內容是業務語言、不含技術細節，方便非技術人員（需求提出單位）核對。
3. 自動產出一份「系統設計文件」，給主管看的部分要能在幾分鐘內看懂做什麼、為何做、成本與風險；給工程師看的部分則要有足夠的技術細節可以直接動工。
4. 自動產出「開發任務清單」，每個任務標明負責角色（前端/後端/QA/DevOps）與執行方式（AI 可獨立完成 / 需要人工操作）。
5. 開發任務清單能自動在 Jira 建立對應的票，不用人工複製貼上。
6. 網頁上有進度儀表板，即時顯示 Jira 票的狀態（讀取，不寫回）。

## 優先順序

| 優先度 | 項目 |
|---|---|
| Must | 需求文件產出 |
| Must | 系統設計文件產出（含主管摘要） |
| Must | 開發任務清單產出（含角色與 AI/人工標記） |
| Must | Jira API 自動建票（經由 n8n workflow） |
| Should | 獨立網頁：瀏覽文件、進度儀表板（查詢用途，不含需求輸入；核心跑通後的下一階段，不阻塞核心驗收） |

## 範圍邊界（不做的事）

- 不做 Jira 票狀態寫回文件（儀表板只顯示，不同步回 tasks-*.md）
- 不做權限分群控制（不管理誰能看哪份文件）
- 本版不做 Notion 整合（見下方「已知缺口」，留待下一版）

## 已知缺口（留待下一版）

- **文件事後編輯機制未定義**：文件產出後，目前只能透過重新跑 `/addyosmani-saspec` 對話修正，或直接編輯 `.md` 檔案，沒有給非技術人員（需求提出單位、主管）自行修改的介面。原規劃考慮用 Notion 當編輯介面，本版先不做，待有實際需求時再補。
- **網頁沒有需求輸入功能**：原規劃網頁上有輸入需求的表單，實作後發現送出只能存成 `_idea/` 檔案，實際產文件仍要回來跟 Claude Code 對話，等於多繞一圈、沒有實質省事，已移除。網頁目前純粹是查詢用途（瀏覽文件、看進度）。真正要有「網頁直接輸入需求就自動產文件」的體驗，需要後端接 Claude API 自己完成整個 saspec 流程，屬於下一版才考慮的大工程。

## 驗收條件

| 情境 | 操作 | 預期結果 |
|---|---|---|
| 產出需求文件 | 提供一份需求描述 | 產出 `requirement.md`，內容為業務語言，無技術細節 |
| 產出系統設計文件 | 需求文件確認後執行下一階段 | 產出 `design.md`，開頭有主管摘要段落，後段有技術細節 |
| 產出開發任務清單 | 設計文件確認後執行下一階段 | 產出 `tasks-*.md`，每個任務有角色標籤與 🤖/👤 標記 |
| Jira 自動建票 | 開發任務清單確認後觸發 n8n workflow | Jira 專案中出現對應數量的票，標題與標籤與 tasks 文件一致 |
| 網頁瀏覽文件 | 文件產出後開啟網頁 | 網頁上可看到產出的文件內容 |
| 進度儀表板 | 開啟網頁進度頁 | 顯示 Jira 各票即時狀態，不影響 tasks-*.md 內容 |
